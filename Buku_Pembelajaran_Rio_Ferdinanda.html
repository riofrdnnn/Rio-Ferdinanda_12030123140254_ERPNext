1.1 Arsitektur Sistem ERPNext dan Frappe Framework

Sistem Enterprise Resource Planning (ERP) modern dituntut untuk menyajikan tingkat ketangkasan data yang tinggi, arsitektur modular, dan kemampuan integrasi yang menyeluruh antar-lini fungsional organisasi bisnis. Pada era transformasi digital saat ini, pemisahan data manual (silo) antar-departemen—seperti gudang, produksi, pemasaran, dan pembukuan—merupakan sumber inefisiensi utama yang memicu disparitas saldo persediaan, keterlambatan pengiriman, dan distorsi laporan keuangan.

ERPNext hadir sebagai solusi ERP terintegrasi open-source paling tangguh dan komprehensif di dunia bisnis saat ini. ERPNext dirancang untuk mengelola seluruh spektrum operasi bisnis modern, mencakup akuntansi umum, manajemen persediaan multi-gudang, manajemen manufaktur (perencanaan kebutuhan material / MRP), manajemen pengadaan (procurement), penjualan (order-to-cash), hingga sumber daya manusia (HRMS). Secara arsitektural, ERPNext tidak dibangun secara monolitik kaku, melainkan berjalan sepenuhnya di atas Frappe Framework, sebuah full-stack web application framework berbasis bahasa pemrograman Python di sisi server (backend) dan JavaScript/TypeScript di sisi peramban web (frontend).

Pemisahan yang tegas antara Frappe Framework sebagai fondasi komputasi dan ERPNext sebagai aplikasi bisnis memberikan keunggulan arsitektural yang sangat signifikan dibandingkan sistem komersial berbayar mahal lainnya. Frappe menyediakan seluruh blok infrastruktur aplikasi enterprise modern, yang meliputi:

  • DocType Metadata Architecture: Dalam Frappe, setiap model data, tabel basis data, tampilan formulir, izin hak akses, dan logika validasi didefinisikan sebagai DocType. Skema basis data MariaDB digenerasi secara dinamis berbasis representasi JSON dari DocType, memungkinkan perubahan model bisnis secara fleksibel tanpa merusak struktur relasi dasar.
  • Object-Relational Mapping (ORM) Berperforma Tinggi: Pengembang dan pengguna dapat berinteraksi dengan entitas bisnis melalui objek Python yang intuitif (seperti frappe.get_doc(), doc.insert(), dan doc.submit()) tanpa harus menyusun kueri SQL mentah yang rentan terhadap galat injeksi dan inkonsistensi data.
  • Role-Based Access Control (RBAC): Sistem keamanan berjenjang yang memetakan otorisasi dokumen berdasarkan peran pengguna (misal: Manajer Gudang, Operator Produksi, Akuntan, dan Auditor).
  • Asynchronous Task Queue: Pemrosesan tugas latar belakang (background jobs) yang dikelola oleh Redis dan pustaka RQ (Redis Queue), memastikan transaksi akuntansi bernilai tinggi dan pencetakan faktur masal tidak membebani kinerja peramban web pengguna.
  • Event-Driven Accounting Hooks: Sistem hook yang secara otomatis memicu penjurnalan buku besar saat dokumen operasional berstatus Submitted (docstatus = 1) dan secara otomatis membalik jurnal saat dokumen di-Cancel (docstatus = 2).

1.2 Peran Docker Desktop & WSL2 dalam Lingkungan Pengembangan Kontainer

Dalam praktik operasional perguruan tinggi dan industri, konfigurasi perangkat lunak enterprise pada komputer personal lokal sering kali terbentur oleh variasi sistem operasi, benturan versi pustaka Python, konflik port jaringan, dan dependensi pustaka C yang rumit (dikenal sebagai kendala "it works on my machine"). Teknologi kontainerisasi menggunakan Docker Desktop menyelesaikan tantangan ini dengan mengemas aplikasi beserta seluruh pustaka, konfigurasi runtime, dan variabel lingkungannya ke dalam kontainer-kontainer terisolasi yang dapat dijalankan secara konsisten pada sistem operasi apa pun.

Pada sistem operasi Microsoft Windows 10/11, Docker Desktop memanfaatkan keunggulan Windows Subsystem for Linux 2 (WSL 2). WSL 2 mengoperasikan kernel Linux asli (Ubuntu) di dalam mesin virtual hypervisor berbobot ringan (lightweight utility VM) yang mengalokasikan memori dinamis dan menghasilkan efisiensi sistem IO mendekati performa komputasi bare-metal. Arsitektur multi-kontainer ERPNext dikelola menggunakan docker-compose.yml yang mengorkestrasi beberapa layanan inti:

  1. Kontainer Frontend (Web Server & Reverse Proxy): Menjalankan Nginx dan Socket.io untuk melayani antarmuka web, file aset statis, serta websocket notifikasi real-time pada port publik 8080:8080 (atau 8081:8080).
  2. Kontainer Backend (Application Server): Menjalankan Python WSGI Gunicorn, bertanggung jawab mengeksekusi logika bisnis Frappe/ERPNext dan mengoperasikan worker asinkron.
  3. Kontainer Basis Data Relasional (MariaDB 11.8): Basis data relasional enterprise terkonfigurasi khusus dengan format baris Dinamis (Barracuda engine) dan dukungan karakter UTF-8 multibyte.
  4. Kontainer Cache & Antrean (Redis): Terdiri dari Redis Cache untuk menyimpan sesi pengguna serta Redis Queue untuk mengelola antrean pengiriman email dan kalkulasi persediaan.

1.3 Pengenalan AI Agent Assistant Google Antigravity IDE

Google Antigravity IDE merupakan lingkungan pengembangan mutakhir yang dilengkapi dengan Autonomous AI Coding Agent terintegrasi. AI Agent bertindak sebagai asisten rekayasa sistem yang cerdas, yang mampu memahami instruksi bahasa alami praktikan dan menerjemahkannya ke dalam serangkaian perintah terminal Linux bash, perintah CLI bench Frappe, atau kueri Python ORM secara otomatis.

Karakteristik paling fundamental yang membedakan Antigravity IDE dari asisten AI konvensional adalah penerapan prinsip Strict Approval Prompting (Tata Kelola Human-in-the-Loop). Dalam konteks Sistem Informasi Akuntansi, integritas data adalah harga mati; sebuah perintah yang memodifikasi basis data keuangan tidak boleh dieksekusi tanpa otorisasi manusia. Oleh karena itu, Antigravity IDE mewajibkan AI Agent untuk menyusun rencana kerja terperinci, berhenti sejenak sebelum mengeksekusi tindakan berisiko, dan menunggu persetujuan eksplisit dari praktikan sebelum perintah dijalankan.

1.4 Pengenalan NotebookLM sebagai Knowledge Management System (KMS)

Google NotebookLM dimanfaatkan sebagai Sistem Manajemen Pengetahuan (Knowledge Management System) terpusat yang dirancang khusus untuk memandu proses pembelajaran praktikum. Berbeda dengan model bahasa publik yang berpotensi menghasilkan informasi halusinasi, NotebookLM beroperasi berbasis prinsip Grounded-Source Synthesis.

Seluruh jawaban, formula biaya manufaktur, pemetaan bagan akun (Chart of Accounts), dan alur jurnal akuntansi yang dihasilkan oleh NotebookLM bersumber langsung 100% dari dokumen acuan yang diunggah oleh pengguna (seperti manual resmi ERPNext, repositori GitHub Frappe, standar akuntansi PSAK/SAK Indonesia, dan dokumen spesifikasi dataset). Sinergi antara NotebookLM sebagai penyimpan dan penalar pengetahuan akuntansi dan Antigravity IDE sebagai enjin eksekusi komputasi membentuk paradigma baru praktikum akuntansi modern yang presisi, adaptif, dan bebas dari halusinasi data.

Dengan prompt ini, AI Agent secara disiplin menyusun proposal rencana tindakan untuk satu tahapan, menampilkan ringkasan data yang akan diproses, dan menghentikan proses sementara untuk menunggu izin resmi praktikan. Praktikan memvalidasi usulan tersebut dan mengetikkan kalimat persetujuan:

3.1 Modul Akuntansi dan Keuangan (Accounting & Finance)

Modul Akuntansi merupakan episentrum konsolidasi informasi keuangan pada ERPNext Version 16. Berbeda dengan aplikasi akuntansi pembukuan sederhana yang mengandalkan penjurnalan manual, ERPNext beroperasi berbasis filosofi Automated Double-Entry Bookkeeping. Seluruh pergerakan aset fisik, siklus pengadaan material, pemakaian bahan baku di lini perakitan, dan pengiriman barang ke konsumen secara langsung memicu pembuatan ayat jurnal buku besar (General Ledger Entries / GL Entries) secara seketika (real-time) tanpa intervensi pengetikan manual.

Fitur-fitur utama pada modul akuntansi ERPNext v16 mencakup:

  • Hierarchical Chart of Accounts (COA): Pengorganisasian bagan akun berbentuk struktur pohon bertingkat (Tree Structure) yang membagi akun menjadi 5 klasifikasi fundamental: Asset, Liability, Equity, Income, dan Expense. ERPNext v16 membedakan secara tegas antara Akun Grup (Group Account) yang berfungsi sebagai penampung saldo konsolidasi dan Akun Buku Besar (Ledger Account) yang menjadi tujuan langsung pencatatan transaksi.
  • Real-Time Sub-Ledger & Control Accounts: Manajemen buku pembantu Piutang Usaha (Accounts Receivable) dan Utang Usaha (Accounts Payable) yang terkontrol secara otomatis melalui akun pengendali (Control Account). Setiap kali transaksi rekanan dibukukan, sistem memvalidasi batas kredit (Credit Limit) dan menghitung umur piutang (Aging Analysis).
  • Multi-Currency & Forex Revaluation: Kemampuan mencatat transaksi dalam berbagai mata uang internasional (seperti USD, EUR, JPY) dengan kurs transaksi harian, serta menyediakan fitur revaluasi saldo valuta asing pada akhir periode akuntansi sesuai standar PSAK 10.
  • Pajak Terintegrasi (Tax Templates): Konfigurasi otomatis pemungutan Pajak Pertambahan Nilai (PPN 11%) dan Pajak Penghasilan (PPh 22 / PPh 23) yang dapat diintegrasikan dengan modul penjualan dan pembelian.
  • Pelaporan Keuangan Dinamis: Penerbitan laporan keuangan standar enterprise seperti Trial Balance (Neraca Saldo), Balance Sheet (Neraca), Profit and Loss Statement (Laporan Laba Rugi Komprehensif), dan Cash Flow Statement (Laporan Arus Kas) yang dapat diekspor ke format PDF maupun spreadsheet Excel.

3.2 Modul Persediaan dan Gudang (Stock & Supply Chain)

Modul Persediaan mengelola pergerakan barang fisik dan valuasi persediaan di seluruh lokasi fasilitas perusahaan. ERPNext menerapkan sistem Perpetual Inventory Valuation, di mana nilai persediaan yang tercatat pada neraca keuangan selalu sinkron dengan saldo kuantitas fisik di gudang setiap detik transaksi terjadi.

Karakteristik penting pada modul persediaan meliputi:

  1. Master Item Komprehensif: Pendaftaran atribut spesifikasi barang, kode SKU/barcode unik, satuan pengukuran standar (Unit of Measure / UOM seperti Nos, Batang, Batang, Kaleng, Kg), serta penetapan metode valuasi resmi (FIFO atau Moving Average).
  2. Hierarki Multi-Warehouse: Struktur pergudangan pohon yang memungkinkan pembagian lokasi penyimpanan logis maupun fisik. Pada industri manufaktur, gudang dipisahkan menjadi:
    • Gudang Bahan Baku (Stores): Menyimpan material mentah yang diterima dari pemasok sebelum diproses.
    • Gudang Barang Dalam Proses (Work In Progress / WIP): Area transit dan penampungan komponen selama pengerjaan di lantai pabrik.
    • Gudang Produk Jadi (Finished Goods): Fasilitas penyimpanan produk jadi siap jual yang memenuhi standar kendali mutu (QC).
    • Gudang Scrap / Reject: Area penampungan sisa potongan material, serbuk kayu, atau komponen cacat.
  3. Landed Cost Voucher (LCV): Fitur untuk mengkapitalisasi biaya pengangkutan (freight), asuransi pengiriman, dan bea masuk kepabeanan ke dalam nilai perolehan harga pokok persediaan bahan baku secara proporsional.
  4. Stock Reconciliation & Stock Ledger: Laporan audit historis (Stock Ledger) yang melacak kartu stok individual secara kronologis, serta modul Stock Reconciliation untuk mencatat hasil inventarisasi fisik (stock opname).

3.3 Modul Manufaktur (Manufacturing & MRP)

Modul Manufaktur mengendalikan proses transformasi bahan baku mentah menjadi produk bernilai tambah melalui tahapan perakitan yang terencana. Modul ini merupakan inti operasional bagi industri Make-to-Stock (MTS) maupun Make-to-Order (MTO).

Arsitektur modul manufaktur terdiri dari 4 komponen kunci:

  • Workstation (Stasiun Kerja): Fasilitas fisik atau lini kerja tempat aktivitas produksi dijalankan (misal: Mesin Pemotongan, Mesin Las, Ruang Cat Duco, dan Meja Perakitan). Setiap Workstation memiliki konfigurasi Hour Rate (tarif biaya overhead dan tenaga kerja per jam) yang menjadi dasar penyerapan biaya konversi.
  • Operation (Operasi Pabrik): Definisi unit pekerjaan standar (seperti Pemotongan Kayu, Pengelasan Rangka, Finishing Cat, dan Perakitan Ergonomis).
  • Bill of Materials (BOM): Formula resep rancang bangun teknis yang memuat rasio kebutuhan bahan mentah per satu unit produk jadi, routing urutan stasiun kerja yang harus dilalui, durasi pengerjaan standar (dalam menit), serta kalkulasi biaya standar (Standard Costing).
  • Work Order (Surat Perintah Kerja): Dokumen instruksi formal untuk memulai rangkaian produksi pada target kuantitas tertentu. Work Order secara otomatis menerbitkan Job Cards untuk setiap stasiun kerja dan mengontrol dokumen Stock Entry (Transfer Bahan Baku ke WIP serta Penyelesaian Barang Jadi).

3.4 Modul Penjualan dan Pembelian (Sales & Procurement)

Siklus komersial pada ERPNext v16 menghubungkan interaksi eksternal dengan vendor dan konsumen secara mulus:

  • Siklus Pengadaan (Procurement Cycle): Dimulai dari pengajuan kebutuhan (Material Request), permintaan penawaran (Request for Quotation), pesanan pembelian resmi (Purchase Order / PO), penerimaan barang fisik di dermaga gudang (Purchase Receipt), pencatatan faktur tagihan pemasok (Purchase Invoice), hingga pengeluaran kas (Payment Entry).
  • Siklus Penjualan (Order-to-Cash Cycle): Dimulai dari penawaran harga kepada calon pembeli (Quotation), penandatanganan pesanan jual (Sales Order / SO), penerbitan surat jalan dan pengeluaran barang jadi (Delivery Note), penerbitan faktur tagihan (Sales Invoice), hingga penerimaan pelunasan piutang (Payment Entry).

3.5 Kustomisasi Sistem DocType dan Pembaruan ERPNext Version 16

Salah satu keunggulan terbesar ERPNext Version 16 adalah kemampuannya untuk dikustomisasi tanpa mengubah kode inti framework (Low-Code / No-Code Extensibility):

  • Custom Field & Form Builder: Menambahkan kolom data baru secara visual (seperti NIK Pengemudi, Nomor Polisi Truk, atau Sertifikat Kayu FSC).
  • Client Scripts (JavaScript): Mengatur validasi interaktif di browser pengguna, kalkulasi diskon otomatis, atau peringatan batas stok minimum.
  • Server Scripts & Webhooks (Python): Mengintegrasikan sistem dengan API perbankan nasional, kurir logistik pihak ketiga, atau pelaporan pajak elektronik e-Faktur.
  • Peningkatan Kinerja Version 16: Version 16 memperkenalkan optimalisasi konektor basis data MariaDB berbasis bahasa C yang mempercepat eksekusi kueri agregasi persediaan hingga 50%, antarmuka pengguna berbasis Workspace yang lebih bersih, serta pelacakan silsilah nomor seri dan batch (Batch Traceability) yang lebih ketat.

Kasus: Pada tanggal 10 Oktober 2026, PT Rio Ferdinanda Manufaktur menerbitkan Purchase Order (PO-00101) kepada CV Kayu Lestari Abadi untuk pembelian 40 lembar papan kayu solid jati belanda @ Rp 45.000 (Total Rp 1.800.000). Pada tanggal 12 Oktober 2026, kayu tiba di Gudang Bahan Baku dan diterbitkan Purchase Receipt (MAT-PRE-2026-00010). Faktur resmi tagihan dari vendor baru diterima pada tanggal 18 Oktober 2026 (ACC-PINV-2026-00010).
Instruksi: Hitung nilai transaksi dan susunlah seluruh ayat jurnal buku besar yang dibukukan oleh ERPNext pada tanggal 12 Oktober dan 18 Oktober 2026!

Pembahasan dan Kunci Jawaban:

  1. Kalkulasi Nilai Pengadaan: 40 Lembar x Rp 45.000/Lembar = Rp 1.800.000,00.
  2. Pencatatan pada Tanggal 12 Oktober 2026 (Penerbitan Purchase Receipt):
    Saat barang diterima secara fisik namun faktur belum terbit, ERPNext mencatat akrual persediaan:
    Akun PerkiraanDebet (IDR)Kredit (IDR)
    (D) 1131 - Persediaan Bahan Baku UtamaRp 1.800.000-
    (K) 1136 - Stock Received But Not Billed-Rp 1.800.000
  3. Pencatatan pada Tanggal 18 Oktober 2026 (Penerbitan Purchase Invoice):

    Akun PerkiraanDebet (IDR)Kredit (IDR)

    (K) 2111 - Utang Dagang Pemasok-Rp 1.800.000

6.2 Soal Kasus 2: Perhitungan Biaya Standar & Formula BOM Multi-Level

Kasus: Tim R&D merancang produk baru yaitu Rak Buku Sudut Industrial RF-200 (PROD-RAK-01). Satu unit rak buku membutuhkan bahan baku langsung: 2 papan kayu jati belanda (@ Rp 45.000), 1 batang pipa hollow (@ Rp 65.000), 12 buah baut sekrup (@ Rp 1.500), 0.3 kaleng cat duco (@ Rp 85.000), dan 1 lembar amplas (@ Rp 3.500). Routing pengerjaan membutuhkan: Stasiun Potong (20 menit @ Rp 35.000/jam), Stasiun Las (30 menit @ Rp 45.000/jam), dan Stasiun Finishing (15 menit @ Rp 40.000/jam).
Instruksi: Hitunglah rincian total Direct Material, Direct Labor & FOH (Biaya Konversi), dan tentukan Harga Pokok Produksi (HPP) standar per unit di modul Bill of Materials (BOM)!

Pembahasan dan Kunci Jawaban:

  1. Biaya Bahan Baku Langsung (Direct Material):
    • Papan Kayu: 2 x Rp 45.000 = Rp 90.000
    • Pipa Hollow: 1 x Rp 65.000 = Rp 65.000
    • Baut Sekrup: 12 x Rp 1.500 = Rp 18.000
    • Cat Duco: 0.3 x Rp 85.000 = Rp 25.500
    • Kertas Amplas: 1 x Rp 3.500 = Rp 3.500
    • Total Direct Material = Rp 202.000,00
  2. Biaya Operasi Konversi (Direct Labor & Factory Overhead):
    • Stasiun Potong: (20 / 60) jam x Rp 35.000 = Rp 11.666,67
    • Stasiun Las: (30 / 60) jam x Rp 45.000 = Rp 22.500,00
    • Stasiun Finishing: (15 / 60) jam x Rp 40.000 = Rp 10.000,00
    • Total Biaya Konversi Operasional = Rp 44.166,67
  3. Total Harga Pokok Produksi Standar (BOM Unit Cost):
    HPP Standar = Rp 202.000,00 + Rp 44.166,67 = Rp 246.166,67 per unit.

6.3 Soal Kasus 3: Alokasi Biaya Tenaga Kerja & Overhead Pabrik pada Stock Entry

Kasus: PT Rio Ferdinanda Manufaktur menerbitkan Work Order untuk memproduksi 10 unit Meja Belajar Minimalis RF-100. Biaya bahan baku yang ditransfer dari gudang bahan baku ke WIP adalah Rp 1.342.500. Biaya operasi stasiun kerja aktual yang dialokasikan ke pengerjaan adalah Rp 437.500 (terdiri dari BTKL Rp 250.000 dan BOP Rp 187.500). Seluruh 10 unit meja selesai dirakit 100% dan dipindahkan ke Gudang Barang Jadi.
Instruksi: Buatlah ayat jurnal penyerapan biaya manufaktur yang dibukukan secara otomatis oleh dokumen Stock Entry Type Manufacture di ERPNext!

Pembahasan dan Kunci Jawaban:

Saat dokumen Stock Entry (Manufacture) di-submit, sistem mengkapitalisasi seluruh biaya bahan baku dan biaya konversi ke dalam aset persediaan produk jadi:

Akun Perkiraan Buku BesarDebet (IDR)Kredit (IDR)
(D) 1134 - Persediaan Barang Jadi (Finished Goods)Rp 1.780.000-
(K) 1133 - Persediaan Barang Dalam Proses (WIP)-Rp 1.342.500
(K) 5211 - Biaya Tenaga Kerja Langsung Diserap-Rp 250.000
(K) 5311 - Biaya Overhead Pabrik Diserap-Rp 187.500

Analisis Akuntansi: Saldo akun persediaan WIP di neraca kembali menjadi nol (habis terserap), sementara nilai persediaan barang jadi mencerminkan biaya perolehan penuh (full absorption costing) sebesar Rp 178.000 per unit.

6.4 Soal Kasus 4: Penjualan Kredit, Pengakuan HPP, dan Pengakuan Piutang Usaha

Kasus: Pada tanggal 22 Oktober 2026, PT Rio Ferdinanda Manufaktur mengirimkan 8 unit Meja Belajar Minimalis kepada Toko Furnitur Indah Abadi via Delivery Note. Harga jual ditetapkan Rp 475.000 per unit (Total Nilai Penjualan Rp 3.800.000), dengan HPP perolehan Rp 178.000 per unit (Total HPP Rp 1.424.000). Pada tanggal yang sama, diterbitkan Sales Invoice dengan termin pembayaran kredit 30 hari.
Instruksi: Buatlah ayat jurnal berpasangan yang terbentuk pada Delivery Note dan Sales Invoice, serta hitunglah Laba Kotor dan Gross Profit Margin dari transaksi tersebut!

Pembahasan dan Kunci Jawaban:

  1. Jurnal pada Delivery Note (Pengeluaran Barang Fisik & Beban HPP):
    Akun PerkiraanDebet (IDR)Kredit (IDR)
    (D) 5111 - Beban Pokok Penjualan (HPP)Rp 1.424.000-
    (K) 1134 - Persediaan Barang Jadi-Rp 1.424.000
  2. Jurnal pada Sales Invoice (Pengakuan Piutang & Pendapatan Penjualan):
    Akun PerkiraanDebet (IDR)Kredit (IDR)
    (D) 1121 - Piutang Dagang LokalRp 3.800.000-
    (K) 4111 - Pendapatan Penjualan Produk Meja-Rp 3.800.000
  3. Perhitungan Laba Kotor & Margin:
    • Laba Kotor (Gross Profit) = Rp 3.800.000 - Rp 1.424.000 = Rp 2.376.000,00
    • Gross Profit Margin = (Rp 2.376.000 / Rp 3.800.000) x 100% = 62,53%.

Pada hari yang sama, bagian keuangan membayar utang kepada PT Baja Logam Nusantara sebesar Rp 1.300.000 melalui transfer bank yang dikenakan biaya administrasi transfer antar-bank sebesar Rp 6.500.

Bab ini menyajikan panduan tutorial operasional langkah demi langkah (18 langkah praktis) yang mendokumentasikan pelaksanaan riil praktikum terintegrasi menggunakan perantara Google Antigravity IDE, Docker Desktop (WSL2), dan ERPNext v16:

8.3 Analisis Kelebihan, Keterbatasan, dan SWOT Implementasi ERPNext

Evaluasi menyeluruh terhadap penerapan ERPNext v16 pada lingkungan perakitan manufaktur dirumuskan melalui matriks analisis SWOT:

  • Strengths (Kekuatan Internal):
    • Zero License Cost: Berbasis open-source bebas royalti, menghemat anggaran investasi teknologi hingga ratusan juta rupiah dibanding SAP atau Oracle.
    • Truly Integrated Monolith: Modul akuntansi, inventaris, pengadaan, dan perakitan berada dalam satu basis data MariaDB tanpa memerlukan middleware API yang rapuh.
    • Automated Perpetual Engine: Meniadakan kebutuhan penyesuaian periodik manual dan menghilangkan distorsi informasi antara gudang dan neraca.
  • Weaknesses (Kelemahan Internal):
    • Technical Overhead: Menuntut pemahaman dasar mengenai manajemen kontainer Linux/WSL2 dan arsitektur Docker Compose.
    • Localization Effort: Pelaporan pajak spesifik Indonesia (seperti e-Faktur PPN CSV dan bukti potong PPh Unifikasi) memerlukan modul lokalisasi pihak ketiga atau kustomisasi skrip mandiri.
  • Opportunities (Peluang Eksternal):
    • AI Synergy: Kolaborasi antara enjin eksekusi Google Antigravity dan pusat pengetahuan Google NotebookLM membuka era baru implementasi ERP yang sangat cepat, adaptif, dan minim galat manusia.
    • Kesiapan Transformasi UMKM: Solusi ini sangat ideal untuk diadopsi oleh ribuan industri manufaktur menengah dan kecil di Indonesia menuju era Industri 4.0.
  • Threats (Tantangan Eksternal):
    • Disiplin Input Lapangan: Keberhasilan kalkulasi biaya manufaktur sangat bergantung pada kedisiplinan operator lini produksi dalam mengisi tiket kerja Job Cards dan mencatat kuantitas scrap material secara jujur.

8.4 Kesimpulan & Rekomendasi Masa Depan

Berdasarkan kajian teoritis komprehensif dan simulasi empiris end-to-end yang dilaksanakan pada PT Rio Ferdinanda Manufaktur, dapat ditarik beberapa kesimpulan pokok:

  1. ERPNext v16 yang dijalankan di atas Frappe Framework dan infrastruktur kontainer Docker Desktop (WSL2) terbukti menjadi fondasi Sistem Informasi Akuntansi yang sangat tangguh, stabil, dan presisi dalam mengelola operasi manufaktur perakitan terintegrasi.
  2. Mekanisme Perpetual Inventory Engine bekerja secara konsisten tanpa anomali, di mana setiap penerimaan bahan baku, mutasi ke lini kerja, penyelesaian perakitan barang jadi, dan pengiriman surat jalan ke pelanggan secara otomatis membukukan ayat jurnal berpasangan yang seimbang ke dalam buku besar.
  3. Kinerja finansial simulasi perakitan dan penjualan 10 unit Meja Belajar Minimalis RF-100 mencatatkan pendapatan bersih Rp 4.750.000,00, HPP Rp 1.780.000,00, serta laba kotor sebesar Rp 2.970.000,00 (Gross Profit Margin 62,53%), dengan saldo persediaan barang dalam proses (WIP) terserap tuntas sebesar Rp 0 pada akhir siklus.
  4. Penerapan mekanisme Strict Approval Prompting pada Google Antigravity IDE menjamin prinsip tata kelola sistem yang aman (safe agentic engineering), di mana pengguna manusia tetap memegang kendali penuh atas setiap manipulasi data dan eksekusi transaksi keuangan.
